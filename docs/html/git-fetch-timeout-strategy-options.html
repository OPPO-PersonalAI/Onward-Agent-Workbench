Git fetch 超时策略：现状 vs 候选方案

BUG-0005 后续 · 代码基线 4c4580d · 分支 20261022-candidate · 2026-10-26

0 · 需要你决定什么

一个策略问题：后台 / 手动 fetch 应该在什么情况下被终止？

现在是"运行满 20 秒就终止"，不管它是卡住了，还是正在正常下载。Project_Books_Translation 这次要下载 87.9 MiB，正常下载就需要 20 多秒，结果每次都在 20 秒被终止，已下载的部分作废，下一次又从零开始，所以永远不会成功。

超时属于调度策略。按项目规则，要由你选定方案之后才能改代码。本文档列出 4 个方案和我的推荐。

已经确认、正在实施的部分（不需要在这里决定）

点击时如果已有 fetch 在运行，就等它完成；后台 fetch 期间按钮也转圈；手动 fetch 失败时显示原因。这些修的是"点了没反应"。"↓N 一直不出现"要靠本文档的决定才能解决。

2 · 候选方案

S1 · git 自带的低速中止 + 总上限 推荐

在 fetch 的环境变量里加上 GIT_HTTP_LOW_SPEED_LIMIT 和 GIT_HTTP_LOW_SPEED_TIME：下载速度持续低于阈值超过指定秒数才中止，速度一回升计时就重置。ssh 在 GIT_SSH_COMMAND 里加 ServerAliveInterval/CountMax，用来发现对端没有响应。把 20 s 改成一个较长的总上限，作为最后的保障。

由传输层（curl / ssh）判断，能区分"慢但在下载"和"卡住"

只改环境变量和一个常量，代码量最小；不需要解析输出，所以不受 locale 影响

Windows / macOS / Linux 的行为一致，都是 git 和 curl 自己的逻辑

只覆盖 https 和 ssh；file://、git://、ext:: 只能靠总上限

服务端打包大仓库时可能长时间不发数据。git 的 upload-pack 默认每 5 s 发一次 keepalive，通常不会误判，但 GitHub 以外的服务端需要实测

S2 · 解析 --progress 判断是否停滞 + 总上限

加上 --progress（它的优先级高于 --quiet），持续读取 stderr；连续 N 秒没有任何新输出就终止。

和传输协议无关，所有协议都适用

顺便拿到已下载的字节数，可以写进 trace，将来还能把进度显示在界面上（GitHub Desktop 就是这么做的）

要自己实现流式读取和停滞计时器，代码量和测试量明显更大

git 的进度只在计数变化时刷新，每秒最多一次；服务端准备数据的阶段可能长时间没有输出，停滞阈值需要留出余量

S3 · 调大固定超时（例如 60 s 或 120 s）

只改 FETCH_TIMEOUT_MS。GitLens 对所有 git 命令默认用 60 s。

改动最小，只有一行

本质没变：只要需要下载的数据超过"上限 × 速度"，还是永远不会成功（1 MB/s 的网络下，120 s 只够下载 120 MB）

真正卡死的连接要等更久才会被终止，期间一直占着并发名额

S4 · 不设超时

VS Code 和 GitHub Desktop 的做法。

大仓库一定能下载完

一个卡死的连接会永久占用 MAX_CONCURRENT_FETCHES = 3 中的一个名额

配合本轮的"点击时等后台那次完成"，用户的点击也会跟着一直等下去；必须再加一个"取消"按钮

4 · 参数（选 S1 或 S2 时需要定）

参数推荐值说明
GIT_HTTP_LOW_SPEED_LIMIT1000（B/s）低于约 1 KB/s 才算"太慢"。就算 0.1 MB/s 的慢网络也远高于这个值
GIT_HTTP_LOW_SPEED_TIME60（s）速度持续低于阈值 60 s 才中止，给服务端准备数据留出余量
ssh ServerAliveInterval / ServerAliveCountMax15 / 4对端约 60 s 没有响应就断开；保留现有的 ConnectTimeout=10
总上限（S1 / S2 都需要）600 s（10 min）最后的保障，覆盖 file://、ext:: 等协议，以及服务端出现异常行为的情况
S2 的停滞窗口60 s连续 60 s 没有任何 stderr 输出就终止

补充：一次 fetch 最长占用一个并发名额 10 分钟（上限是 3 个），对后台功能来说可以接受。在此期间按钮会一直转圈，用户能看到"正在同步"。

5 · 独立维度：手动 fetch 要不要用不同的上限

选项说明
D1 · 和后台一样 推荐本轮已经确定，点击会等正在运行的那次完成，所以两者本来就会共用同一次 fetch。分成两套上限反而会出现"点击等的那次 fetch 用的是后台的上限"这种情况
D2 · 手动的更宽松只对新启动的手动 fetch 生效；如果点击时已经有后台 fetch 在运行，等的还是后台那一次，效果有限

6 · 附带问题（可以一起决定，也可以以后再说）

问题现状可选做法
被终止后残留的 tmp_pack_*这次残留了 28.7 MB，要等以后 gc 才会删除(a) 选了 S1 / S2 以后很少会被终止，残留问题自然变小，推荐；(b) 终止时清理当次产生的 tmp_pack，需要识别"这个文件是不是这次产生的"，有误删正在进行的 fetch 产生的文件的风险
终端里正在运行 git 网络命令时，后台 fetch 也同时启动这次两者重叠了 20 s，互相抢带宽需要先识别命令的开始（现在只知道命令什么时候结束），工作量较大，建议以后单独做
fetch 失败时，trace 里记录已下载的字节数只能事后去磁盘上查 tmp_pack选 S2 时天然就有；选 S1 时可以在失败时统计一次 tmp_pack 的大小（只读一次目录）

7 · 同类产品

产品超时来源
VS Code（git 扩展）autofetch 不设超时，只能通过取消令牌终止autofetch.ts，git.ts
GitHub Desktop不设超时（dugite 支持 AbortSignal，但 Desktop 没有使用）core.ts
GitLens所有 git 命令默认 60 s，设为 0 表示不限git.ts
JetBrains / GitKraken / Sublime Merge / Fork没有找到相关文档—
git 自带的机制http.lowSpeedLimit/Time：速度持续低于阈值才中止；ssh 用 ServerAliveIntervalhttp.adoc，curl progress.c，ssh_config(5)
为什么推荐 S1，而不是照搬 VS Code / GitHub Desktop 的"不设超时"

那两个产品的 fetch 都是独立的操作，没有"每个仓库最多一个、全局最多 3 个"的并发名额，也没有"点击等后台那次完成"的设计。我们的 fetch 有这两个约束，一个永远不结束的 fetch 会卡住整个仓库的同步按钮。S1 让传输层自己判断"慢"和"卡住"，既能保证大仓库下载完，又保留了对卡死连接的处理。
