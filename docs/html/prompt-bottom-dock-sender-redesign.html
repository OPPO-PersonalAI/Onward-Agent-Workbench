底部停靠 Prompt 面板 · 发送区重排交互稿

目标：把发送区（右侧 Task 列）里那块一直空着的区域用起来。三个颜色点和「添加到历史」从编辑区右侧的 48px 竖栏，搬到发送区、放在 5 个快捷发送按钮上面；Task 卡片的名称改成两行显示。

现状：默认尺寸下发送区约  100px  空白，接近一半 编辑区去掉竖栏后，文本区  +48px  4 版布局 × 2 种卡片样式 我的推荐： 方案 B + 样式 ② 最终选定： 方案 D + 样式 ①（2026-11-25）
决定（v2）
选定 方案 D（卡片撑满）+ 样式 ①（序号 + 名称）。编辑状态的取消 / 保存 / 另存为新一起搬到发送区；左右停靠保持不变。实现细节：卡片每行在 30～96px 之间等高撑满；名称随卡片高度显示 1～4 行；卡片很矮时序号和名称并成一行；卡片很窄时只显示序号。
怎么看这份稿子
第 6 节的交互稿是真的可以操作的：顶部的控制条能调面板高度、发送区宽度、Task 数量、新建 / 编辑状态、界面语言和卡片样式，4 个方案同时跟着变。每个稿子下面有实时测量：发送区空白、文本区宽度，以及「Task 区需要滚动」「有控件被挤出」这类警告。鼠标悬停在按钮上能看到提示文字。

2现状复盘

下面是按现有 CSS 尺寸复刻的现状，条件和你的截图一致：面板高 240px、发送区宽 240px、8 个 Task（4 列 × 2 行）。

① 发送区空白

发送区用 justify-content: space-between 把 Task 网格推到顶、快捷按钮推到底，中间约 100px 没有任何内容。面板拉得越高，空白越大。

② 48px 竖栏占用编辑区宽度

三个颜色点 + 「添加」按钮单独占了一条 48px 宽的竖栏（PROMPT_BOTTOM_ACTION_RAIL_WIDTH），编辑区最小宽度因此是 240 + 48 = 288px。

③ 卡片太窄，只显示序号

8 个 Task 排成 4 列时，每张卡片内容区只有约 37px，小于 44px 的阈值，于是名称被换成序号（@container task-slot (max-width: 44px)）。名称只能靠悬停提示看到。

3我的看法

整体同意这个方向。我觉得它解决了三个实际问题，但有几处细节需要在设计时处理好，否则会带来新的困扰。

同意的理由

空间真的被浪费了

默认尺寸下发送区将近一半是空的。把一行按钮挪进来，加上卡片增高，基本能填满。

编辑区变宽

竖栏去掉后，文本区多出 48px，编辑区最小宽度从 288px 降到 240px，窄窗口下更从容。

操作的位置更统一

「存进历史」和「发给 Task」都是在回答同一个问题：写好的这段文字往哪儿去。左边写，右边决定去向，分工更清楚。

需要注意的地方

1. 颜色点的含义容易被误解

发送区原来只有「发给 Task」的按钮。三个颜色点单独放过去，可能被理解成 Task 的颜色、或某种发送方式。所以需要把它们和「添加到历史」在视觉上绑成一组，并和发送按钮隔开（这就是方案 B 的出发点）。

2. 编辑状态有 6 个控件

编辑已有 Prompt 时，这一行要放 3 个颜色点 + 取消 + 保存 + 另存为新。240px 宽可以放成一行；发送区最窄是 180px，这时只能显示图标或者换行。

3. 面板高度可以调

空白只在默认高度及以上才出现，面板最矮可以到 160px。必须规定好面板变矮时谁先让位，保证按钮永远能点到（见第 8 节）。

4. 名称显示不全，主要是因为卡片太窄

4 列、240px 宽时，卡片内容宽约 37px，一行只能放 5～6 个英文字母，两行大约 10～12 个。比只显示序号好很多，但像 Onward-Agent-Workbench 这样的长名字仍然会被截断。

5. 序号要保留

代码注释里写明了序号和 Cmd+数字 快捷键是对应的。两行样式里序号不能丢，至少要以小号前缀的形式保留。

6. 误点的风险

「存进历史」没有副作用，随时可以删；「发送」发出去就收不回。两行挨得近了以后，需要留出间距或分隔线，按钮样式也要明显不同（颜色点 / 中性按钮 vs 彩色发送块）。

5卡片两行样式

「两行显示」有两种做法，下面在同样的卡片宽度下并排比较。每格放 2 张卡：左边是已选中、名字很长的 Task；右边是没有自定义名称的 Task。中文名称的效果可以在第 6 节的交互稿里看（6 号 Task「前端重构」）。卡片宽度是按真实布局算出来的。

样式 ① 序号 + 名称

第一行是序号（宽度够时显示成 Task 1），第二行是名称，单行加省略号。序号最醒目，和 Cmd+数字 对应得最直接。没有自定义名称时第二行显示「未命名」，这是一处新增文案。

样式 ② 名称折两行

名称本身折成两行，序号以小号前缀放在名称前面（选中时用 Task 的颜色）。能看到的名称字符最多，最贴近你说的「名称两行」。卡片更高时自动放宽到 3～4 行。

6.0基线：现状

用于对照。调控制条时它也会跟着变，可以看到面板越高空白越大。

6.1方案 A · 直接上移（按你的原始思路）

竖栏去掉。发送区从上到下是：Task 网格 → 「颜色点 ··· 添加到历史」一行 → 分隔线 → 快捷发送。卡片固定 44px 高、名称两行；按钮两行贴着底部，剩余的空白留在网格和按钮之间。

优点

  • 最直接，改动量最小
  • 按钮位置固定在底部，不随 Task 数量跳动
  • 「添加到历史」宽度够时显示文字，比纯图标好找

不足

  • 面板高于默认值时空白仍然存在（卡片不长高）
  • 颜色点和「添加」之间只靠位置关联，第一次用的人未必看得出颜色点是「带颜色添加」

6.2方案 B · 分段按钮（推荐）

把「添加到历史」和三个颜色点合成一个分段按钮：[ + 添加到历史 | ● | ● | ● ]。主体是普通添加，右边三格是「带颜色添加」。编辑状态下主体变成「✓ 保存」，取消和另存为新放在两侧。卡片可以从 44px 长到 60px，名称最多显示三行。

优点

  • 一眼能看出颜色点是「添加」的不同方式，降低误解
  • 分段按钮的外框把它和下面彩色的发送块明显区分开
  • 卡片随高度长高，空白最少，又不会像 D 那样过度拉伸
  • 180px 最窄时主体自动只显示图标，编辑态 6 个控件仍在一行内

不足

  • 比 A 多一个新的控件样式（分段按钮），CSS 稍多
  • 每个颜色格只有 26px 宽，比现在的 28px 小一点

6.3方案 C · 分区标题

在 B / A 的基础上，给三个区加小标题：「发送目标 · 已选 2/8」「存入历史」「发送」。已选数量写进标题后，右下角的小格子示意图就不需要了。面板矮于约 235px 时标题自动隐藏，小格子示意图重新出现。

优点

  • 结构最清楚，新用户最容易理解每一块是干什么的
  • 「已选 2/8」比小格子示意图更直观

不足

  • 标题占掉约 45px 高度，在默认高度下几乎刚好放下，稍矮就要隐藏
  • 标题时有时无，界面会跳动
  • 引入 3～4 条新文案（需要中英文）

6.4方案 D · 卡片撑满

按钮两行和 A 一样，但 Task 网格把剩下的高度全部吃掉（每行最高 96px），名称最多 4 行。空白最少，卡片也最好点。

优点

  • 空白几乎为零
  • 卡片大，好点，名称显示得最全

不足

  • 违背了现有代码里有意保留的原则：选择器是 Task 网格的「缩小模型」，1 个 Task 时不应该被放大成一个占半个面板的大块（.prompt-sender-terminals 的注释）。把 Task 数切到 1 或 2 就能看到这个问题
  • 卡片大小随面板高度变化，视觉上不够稳定

从数据看出的问题
在默认高度（240px）下，B 的空白从 104px 降到 20px。但面板拉到 300px 以上时，B 的卡片已经到了 60px 上限，空白又会变多（360px 时还有 140px）。如果你平时会把面板拉得很高，可以考虑把 B 的卡片上限放宽（比如 80px），或者干脆采用 D 的「撑满」，但要接受 1～2 个 Task 时卡片偏大的问题。这一点放在第 10 节的 Q3 里由你决定。

卡片样式（① / ②）和布局方案是两个独立的选择，可以任意组合。我推荐 B + ②：② 正是「名称两行」，序号以小号前缀保留；B 让颜色点的含义一目了然。

8面板变矮时的让位顺序

原则：按钮永远可见、永远能点；先压缩卡片，最后才让 Task 网格滚动。下面以方案 B、8 个 Task、240px 宽为例。

≥ 约 220px卡片到上限卡片 60px，名称最多 3 行；面板再高，多出来的部分才会留白
→
约 190～220px卡片随高度变化卡片在 44～60px 之间，名称 2～3 行
→
< 约 190px卡片退回一行卡片 30px，序号和名称在同一行，和现在差不多
→
160px（最矮）仍然放得下8 个 Task 刚好放下；只有行数更多的自定义布局才会让 Task 网格滚动，按钮两行始终固定在底部

这里的阈值（约 190px / 235px）是按 8 个 Task、两行网格算的。实现时会按实际行数计算，不会写死。

按项目规则，设计前查了成熟产品和平台规范的做法。下面每条都标了可信度：原文 表示直接读到了官方页面原文；摘要 表示来自检索结果的转述，没有逐字核对；未查到 表示没有找到可靠资料。

问题别人怎么做对本次设计的意义
主操作和它的变体怎么组合 原文 Windows 的 SplitButton：一半立即执行主操作，另一半弹出更多选项，两部分可以分别点击。
原文 Apple HIG：每个视图里醒目的按钮保持一到两个；用样式而不是尺寸区分首选项，尺寸相同的一组按钮表示它们是并列选项。
摘要 GitHub Primer 的 ButtonGroup：一组里最多一个 primary，放在末尾；按钮组加 role="toolbar" 后辅助技术才把它当成一组。		 支持方案 B 把「添加」和颜色点做成一组。区别是：我们的颜色格是直接执行的，不是弹出菜单，所以更接近「按钮组」而不是严格意义上的 SplitButton。实现时给这一组加 role="group" 和组标签（现在的颜色选择器已经有）。
「本地保存」和「发送」该放一起还是分开 未查到 没有找到任何资料直接讨论这个问题；GitHub 评论按钮、Gmail / Slack 定时发送、Copilot Chat / Cursor 输入栏的具体布局都没有查到原文。
原文 Windows 按钮指南：动作很多时，先用复选框 / 单选框让用户选，再用一个命令按钮统一执行。		 没有现成的先例，分开还是合并要靠我们自己判断。后一条和「先选 Task、再点发送」的结构一致，说明发送区现在的结构本身是合理的。
终端产品怎么选「发给哪些 pane」 原文 iTerm2 的 Broadcast Input：在菜单里选范围（仅当前 / 当前 tab 全部 / 所有 tab），也可以逐个 pane 开关；正在接收的 pane 本身显示红色条纹背景。
摘要 Windows Terminal 1.19 和 Warp 也是「选范围 + 快捷键」，没有集中的目标列表。
未查到 tmux、WezTerm、Wave。		 查到的终端产品都没有「目标小格子」这种选择器，所以格子里怎么显示名称没有先例可以照搬，只能按通用的按钮文字规则来定。
长名称放不进小格子 原文 Windows 按钮指南：文字放不下时，建议加宽按钮或加高按钮并让文字折行，没有提到用省略号。
原文 Apple HIG（macOS）：需要两行文字时使用高度可变的按钮；上下排列的按钮保持相同高度。
原文 VS Code 的 wrapTabs 是让整排 tab 折成多行，不是让单个 tab 内的文字折行。
未查到 「太窄就只显示编号」这种做法的书面依据。		 支持样式 ②（名称折行），也支持所有卡片同一行高（我们的网格每行等高）。现在的「太窄就换成序号」没有找到出处，但作为最窄时的退路仍然合理。
点击区域和颜色 原文 Apple HIG 无障碍页：macOS 控件默认 28×28pt，最小 20×20pt（按钮页另写着点击区域至少 44×44pt，两处说法不一致）。
原文 Apple HIG：不要只靠颜色传达信息，要加形状或文字，特别是考虑红绿色弱。
未查到 Windows Fluent 的最小点击区域原文。		 颜色格 26px、发送块 24px，都在 macOS 最小值以上。颜色点只靠颜色区分是现有的问题，这次不改，但目前要靠悬停提示和 aria-label 补充。如果你在意，可以单独排一项改进。

10需要你决定的事

  1. 用哪一版布局？
    A 直接上移B 分段按钮（推荐）C 分区标题D 卡片撑满组合（比如 B 加上 C 的「已选 2/8」）
    推荐 B：空白最少、颜色点含义最清楚、没有新增文案，最窄宽度下也不会挤。
  2. 卡片用哪种两行样式？
    ① 序号 + 名称② 名称两行（推荐）
    推荐 ②：就是「名称两行」，能看到的名字最多；序号以小号前缀保留，Cmd+数字 的对应关系不丢。
  3. 卡片要不要随面板高度长高？
